## Question for the architect

1. **How should XLSX be read?** Options, with my recommendation first:
   a) **A small in-house reader** (no dependency): an `.xlsx` is a zip of XML. Read the first worksheet,
      shared and inline strings, numbers and cached formula values with `node:zlib` and a ~150-line zip
      directory reader (the repo already has one in `tools/gazetteer/src/zip.ts`). Reading only; the
      XLSX twin of `import-500.csv` would then be written by a matching test-only writer, or committed
      as a binary fixture. About a day; nothing new to audit.
   b) `pnpm.overrides` forcing `uuid@11.1.1` under exceljs. Fast, but it is the override the prompt
      forbids without a ruling, and exceljs has never been tested against uuid 11.
   c) CSV only in WP-17 (papaparse), with XLSX moved to a later WP.
   d) SheetJS from its own CDN tarball (`xlsx` on npm is 0.18.5 with high-severity advisories); that
      is a dependency outside the npm registry and outside `pnpm audit`.

## Design ready for the build (unchanged by the answer except step 4)

- `students.home_department_id` NOT NULL: the form defaults to the managing department, and an import
  with no department column does too; an unknown department is a row error.
- Route tests mint principals through a stub `auth` (as `testing/harness.ts` already does) instead of
  signing in, so WP-17 adds no Argon2id hashing to `pnpm verify`.
- `seed:demo --students` runs on a database that has finished setup (the plain `seed:demo` runs before
  the wizard and has no organization to put students in). It creates a demo professor with **no usable
  password** — an admin resets it through Admin → Users — rather than printing one, which pre-M1 ruled
  out for seeds.
- The shell's file read returns base64 from a small encoder in `files.rs`, so no Rust crate is added.
