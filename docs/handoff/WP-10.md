## 3. Decisions worth the architect's eye

1. **Resolution is by field group, not field by field.** Fee `{feeKnown, feeMinor, feeCurrency, feeText}`,
   prize `{text, total, currency}`, place `{venue … lat, lon, geoPrecision, hostInstitutionId}`, dates
   `{startsAt, endsAt}` and team `{min, max}` are each won by **one** source record. Field-by-field would
   let a total from one source pair with a currency from another, which is exactly the splice "nothing
   converted" forbids. It would also break the `fee_known` and date-order CHECKs. Overrides still apply
   per field on top.
2. **A silent source does not outvote a speaking one.** Resolution prefers claims that state a value:
   `null` and the enums' `"UNKNOWN"` count as silence. "Unknown fee" is stored as *no* `feeKnown` claim, so
   a source that says nothing about money can't beat one that says "Free".
3. **What counts as a conflict.** "Material" follows §7.5: dates more than 1 h apart (60 min exactly is
   not), team size, fee, mode, plus any R63 alternate claim that differs from the selected value.
   `/events/:id/conflicts` also lists non-material differences (for example title wording) with
   `material: false`, because the three-sources scenario asks for "every differing field".
4. **Audit.** Event creation and auto-merges are audited as SYSTEM in the link transaction. Plain
   re-scrape updates are not audited; they live in `event_changes`, which is the product-history table.
   Merge, reject and unmerge are audited as USER.
5. **A new event writes no `event_changes`.** Its first resolution has no "before", and forty rows of
   null → value per new event would bury the changes WP-23 needs to notice.
6. **Unmerge marks the pair REJECTED.** Splitting two events is an administrator saying they are
   different, so the pair should not return to the review queue.

## 4. What happens to each side on merge and unmerge (R66)

| Thing | Merge | Unmerge |
|---|---|---|
| Loser `events` row | kept; `visibility = MERGED`, `merged_into_event_id`, version + 1 | visibility restored to **exactly** what it was, read from the MERGE change row (an ADMIN_HIDDEN stays hidden) |
| Source records, their claims and source deadlines | move to the survivor | the records whose `origin_event_id` is the loser (or an event merged into it) move back |
| Overrides | stay on their own event; the loser's are dormant while it is merged | still in place, so they apply again |
| `event_changes` | stay where written; MERGE rows added (loser visibility, survivor field changes) | UNMERGE rows added |
| Watchlist, `event_user_state` | tables arrive in WP-16a; keyed by event id, so they stay on the loser. WP-16a should follow `merged_into_event_id` when reading | nothing to restore |
| `dedup_candidates` | the pair becomes MERGED; other rows naming the loser remain and are refused with `EVENT_ALREADY_MERGED` | the pair becomes REJECTED |

The survivor is the event with the earlier `first_seen_at`, then the one with more records, then the
lower id.

## 5. Minor decisions

1. The candidate-generation prefilter is a trigram Jaccard of at least 0.2 on the normalized title. It is
   a filter, not a score, so it is not an R65 setting.
2. Features answer 0 when either side is missing the value. Location/mode gives half credit for an
   unknown mode or place, because otherwise one source not naming a venue would count as disagreement.
3. A null `edition_year` on either side is compatible for candidate generation, as R64 says.
4. When a new record is in the grey band against several events, each such pair gets its own PENDING row.
5. `dedup.weights` is one setting (the object schema checks the sum). The candidate < auto-merge check
   spans two keys, so it is enforced in `readDedupConfig`: a bad combination logs a warning and uses the
   defaults.
6. Merged events are left out of the candidate slice. POLICY_HIDDEN events are included.
7. `officialUrl` is only the organizer's URL. The source's own page (`candidate.url`) is never used as
   one, or every CTFtime event would URL-match nothing and everything.
8. Migration 0008 was generated by drizzle-kit with one hand edit: its table-rebuild copy selected the
   two new columns from the old table. The header says so.
9. `run.ts` was at 400 lines. `sourceConfig` moved to `source-row.ts` (now 382).

## 6. Known issues / tech debt

- **`EventsService.createEventFromCandidate` (WP-08b)** now has no production caller; ingest goes
  through the linker. Its §19 policy test still uses it. WP-14's manual entry should use the linker.
- **There is no "split one record out".** An auto-merged record can only be separated by merging and
  unmerging events, not on its own. A MANUAL `match_method` exists for when WP-16b wants this.
- **Stale claims.** A field a source stops stating becomes a `null` claim rather than being removed.
  An alternate claim that disappears is emptied, not deleted.
- **Precision under an override** is set to DATETIME. WP-16b's override editor should decide this
  properly.
- **Cost of a first scrape.** Each record gets 37 claim rows, so a 100-event first scrape writes 3,700
  claims plus one resolution per record. That's fine here; WP-15a's perf test should measure it.
- **Series and recurring rounds** are untouched (WP-11).
