## What was built

- **STEP 0:** spec v1.1.22; R108 (one key, one firing, no burst), R109 (recipients), R110 (severity and toasts),
  R111 (snooze read by the evaluator). §6.2 loses `[OPEN Q4]`; `notification_preferences` gains `toast_enabled`.
- **Contracts** `notifications.ts`: 13 types (§12 + `SOURCE_BLOCKED`, `CREDENTIAL_EXPIRED`), labels, severities,
  `Thresholds`, the DTO (with `dueAt`/precision and a `toast` flag), list/query/snooze/preferences shapes, stream
  payload `{id, unreadCount}`. `NOTIFICATION_NOT_FOUND`, `NOTIFICATION_SNOOZE_INVALID`. `notification.updated`
  added to the stream. `shell.ts`: `TraySetUnread`, `CriticalToast` (route regex), `NAVIGATE_EVENT`.
- **Migration 0030** (`db:generate`): both tables as §6.2, UQ(user_id, dedupe_key), indexes (user_id, read_at,
  snoozed_until) and (snoozed_until), CHECKs from the enums, in-app routes only. The change watermark and the admin
  episode onsets live in `app_meta`.
- **Registry** `modules/notifications/types.ts`: a `Record` over the enum (a bare type does not compile; a test
  checks at run time too). Effective preference = stored ?? default.
- **Domain** `domain/notifications/` (pure, clock-injected): `crossedThresholds` reads WP-22's bucket and
  `daysLeft`; `pickMostUrgent`; `dedupeKey`; `typeForItem`; `severityOf`; `recipientsFor`; `collapseChanges` (one
  per event per run, keyed on the newest change, carrying who changed it); `changeRecipients`; `resurfaceable`.
- **Engine** (`engine.ts`): a `DueItemSink` on WP-22's evaluator (5 min, offline). One run, in order:
  - deadline thresholds;
  - watched-event changes after the watermark (the first run starts the watermark at the latest change, so history
    is not news);
  - admin notices (BLOCKED, credential failed, three failures in a row), keyed on the episode's onset;
  - snooze resurfacing.

  `emit()` honours preferences, inserts-or-ignores and publishes. Machine rows are not audited.
- **Stream:** the hub gains an optional per-user audience, honoured live and on replay; notification events reach
  only the recipient.
- **API:** `GET /notifications?state&cursor&limit`, `GET /notifications/unread-count`,
  `POST /notifications/:id/{read,unread,dismiss,restore}`, `POST /notifications/:id/snooze {until}`,
  `POST /notifications/read-all`, `GET|PUT /me/notification-preferences`. Each change publishes
  `notification.updated` to the person's other windows.
- **UI:**
  - The bell: icon + number, named "3 unread notifications"; a popover of the latest five.
  - The Inbox (`/notifications`): Unread / All, severity icon + word, the due line with its precision, relative
    time. Open goes to the route and marks it read. Read/unread, snooze (1 h, tomorrow 09:00 IST, due day
    09:00 IST, a typed time in Indian time), dismiss with Undo, Mark all read. Guide, skeleton,
    "You're all caught up", error.
  - Preferences: on/off, 14/7/3/2/1 days + due day, toast.
  - Dashboard card: the latest five.
  - `notification.*` events re-read the queries. Under R30 the badge polls every 60 s and says "Live updates
    unavailable".
- **Tray (Rust):**
  - `tray_set_unread`: redraws the icon from the base icon with a red disc and white digits (a built-in 3×5
    bitmap, 1–9 then "9+"), and sets the tooltip "CompIntel — 3 unread notifications".
  - `notify_critical`: a Windows toast via `tauri-winrt-notification`. Clicking it shows, unminimizes and focuses
    the window, then emits `app://navigate`. Both sides accept internal routes only.
  - `tray_badge(health, unread)`: health beats count; `health` is always `None` until WP-30 (documented in
    `badge.rs`).
  - **Debug builds toast under the PowerShell AUMID**, since there is no Start-menu shortcut until WP-31. So the
    toast says "Windows PowerShell", and a click after it has moved to Action Center may open PowerShell.

## Deviations from the prompt

- **`POST /notifications/:id/restore`** was added as the server half of dismiss's Undo, so an Undo survives the app
  closing.
- **Admin notices:** `source_state` has no "state changed at" column. The engine stores each episode's onset in
  `app_meta` (`notifications.adminEpisodes`) and keys on it, so a state that clears and comes back re-arms.
- **"Scraper failing"** = `consecutive_failures ≥ 3` (§12).
- **Snooze's "tomorrow 09:00"** and "due day 09:00" are computed in the UI (Indian time); the server checks that
  `until` is in the future and within 60 days.

## Minor decisions made

- Savers who hid the event get none of its notifications.
- `due_at`/`due_precision` are stored on the row for display and the due-day snooze.
- A watched-event change uses the event title in its notification, never a person's name (R92).
- Toasts are only for notifications created after the window loaded, so nothing old pops up at sign-in.
