Context you must not re-litigate: CLIST is an **aggregator behind an API key the user does not have yet**
(user action U4, OPEN). This WP is therefore **fixture-first and must not block on U4**: everything below is
testable offline, and the live run is conditional.

BUILD:
1. **Key storage.** Settings key `sources.clist.apiKey` (+ `sources.clist.apiUsername`) in the typed registry:
   zod non-empty string, default `""`. The value is **never logged and never exported** (§6.2 footnote) — add
   the settings path to the pino redaction list and to the export/diagnostics denylist, and assert both.
   In `--dev` only, `COMPINTEL_CLIST_API_KEY`/`_USERNAME` may seed it. Admin-only route
   `PUT /api/v1/admin/sources/:key/credential` (audited, body never echoed); the matching GET returns
   `{ isSet: boolean }` and nothing else. No UI this WP.
2. **Source row** (update the WP-09a seed, upsert by key, never clobber `version`): adapter `CLIST_API`,
   `cadence_minutes` 30, `manual_min_interval_minutes` 10, `min_delay_ms` 6000, `max_requests_per_run` 4,
   `allowed_paths_json` = `/api/v4/contest/` and `/api/v4/resource/` only, `attribution_text` =
   "Contest data provided by CLIST", **lowest `trust_rank` of all sources** (aggregator, §7.5),
   `compliance_status` APPROVED_WITH_LIMITS with notes quoting the ToS obligations (rate limits, caching,
   attribution, no redistribution) and the key requirement. Auth shape lives in `config_json`
   (`{"auth":{"header":"Authorization","valueTemplate":"ApiKey {username}:{key}"}}`) so it can be corrected
   without touching code.
3. **The robots tension — decide it in the seed, not in the adapter.** `clist.by/robots.txt` says
   `Disallow: /api/` with `Allow: /api/v*/doc`, while the Terms invite *authenticated* API use. Add an explicit,
   seed-only `config_json.robotsExemption = { paths, reason, reviewedBy, reviewedAt }`. The compliance gate
   honours it **only** when all three hold: the path is in `allowed_paths_json`, the request carries the source
   credential, and the exemption names a reviewer and a date. Everything else on clist.by stays
   ROBOTS_DISALLOWED. Log one line per run stating the exemption was used. **Flag this in the report as a
   proposed ruling** — do not edit ARCHITECTURE.md yourself.
4. **Missing key is a source state, never a crash.** With no key: the run makes **zero requests**, records
   outcome `BLOCKED_BY_POLICY`, `error_kind = BLOCKED`, `error_detail = "CLIST API key not set (U4)"`, updates
   `source_state`, and stays scheduled (no backoff escalation, no failure counter). Same for a blank username.
5. **Adapter** `src/adapters/clist/`: `kind: 'API'`, `needsBrowser: false`, `defaultCadenceMinutes: 30`.
   `listing()` walks `/api/v4/contest/` with `start__gte`/`start__lte` bounding **now − 1 day … now + 90 days**,
   `order_by=start`, `limit=100`, `offset` pagination against `meta.total_count`, ≤ 4 requests/run. A walk that
   completes inside the caps sets `listing_complete = true`; hitting the cap → PARTIAL, `listing_complete = false`
   (A8). `detail()` is not implemented — the listing carries every documented field. `external_key` = `clist:<id>`.
6. **`normalize()` is pure**: `event`→title, `host`/`resource`→organizer/platform, `start`/`end`→UTC instants,
   `duration`, `href`→official/registration URL, `n_problems`→a parse note. `event_type = CODING_CONTEST` via the
   WP-08a/08b policies; mode ONLINE unless the resource says otherwise; timezone absent → UTC with lowered
   precision (§7.3); fee and team size **unknown**, never 0. CLIST exposes no people fields — assert that anyway.
7. **Series / recurring-round detection** — the real deliverable. New pure module `src/domain/series/`
   (no DB, no HTTP; the ESLint boundary rule applies). Input: a normalized candidate + its sibling candidates
   from the same run. Output `{ seriesKey, seriesName, recurrence, isRecurringRound, roundLabel?, confidence }`.
   Rules, in order:
   a. **Resource table** — codeforces.com, leetcode.com, atcoder.jp, codechef.com, topcoder.com, hackerrank.com
      contest paths are round-producing platforms.
   b. **Title patterns** — "Codeforces Round 975 (Div. 2)", "Educational Codeforces Round 175", "Weekly Contest
      412", "Biweekly Contest 141", "AtCoder Beginner Contest 380", "Starters 123". Strip the ordinal to form
      `seriesKey` (normalized, lowercased, no digits) and keep it as `roundLabel`.
   c. **Cadence inference** — ≥ 3 candidates sharing a `seriesKey` with starts ≈ 7 / 14 / 30 days apart →
      WEEKLY / BIWEEKLY / MONTHLY; otherwise IRREGULAR.
   d. Otherwise `isRecurringRound = false`. A one-off named contest, hackathon or CTF is **never** a round.
   e. **Yearly editions** ("HackX 2026") → `recurrence = YEARLY` and `is_recurring_round = false`. That
      distinction is load-bearing: §7.5 never merges across `edition_year`.
   Persistence: upsert `event_series` by normalized key, set `events.series_id` and `events.is_recurring_round`
   inside the item transaction, audited through `withAudit` as SCHEDULER (R35).
8. **Feed vs Contest Calendar.** Add two repository readers in the events module: the main-feed reader filters
   `is_recurring_round = false`, the Contest Calendar reader filters `is_recurring_round = true`. If an events
   list route already exists, give it a `feed=MAIN|CALENDAR` parameter with MAIN as the default. State in the
   handoff that this is the default WP-15a's `EventQuery.includeRecurring` must inherit (false excludes rounds)
   and that WP-16a renders the Contest Calendar tab. **No UI in this WP.**
9. **Fixtures** `apps/backend/test/fixtures/clist/`, hand-built from the documented v4 schema (CLIST was never
   called — §2 of the feasibility report). Every file carries a `_note` field saying it is synthetic and
   derived from the docs, not recorded traffic. Cases: `listing-page1` + `listing-page2` (pagination +
   `meta.total_count`), `listing-recurring` (a Codeforces Round, three LeetCode Weekly Contests two weeks apart,
   an AtCoder ABC), `listing-oneoff` (an ICPC regional and a named 48-hour hackathon), `listing-yearly`,
   `http-401`, `http-429-retry-after`. Goldens through `expectGolden` exactly as WP-09b does; `UPDATE_GOLDEN=1`
   to refresh.
10. **Live run is conditional.** Script `pnpm --filter @compintel/backend clist:smoke` runs one listing request
    **only if** the key is set and setup is complete (A10); otherwise it prints "U4 open — skipped" and exits 0.
    Never create an account, never fall back to website sessions, never scrape clist.by HTML.

TESTS (all in `pnpm verify`, all offline):
- pagination and `listing_complete`; the request cap → PARTIAL; 401 → `HTTP_4XX` with a note that the key may be
  invalid; 429 honours `Retry-After`; the effective delay is ≥ 6 s and ≤ 10 requests/minute (fake `Clock`).
- **no key → `BLOCKED_BY_POLICY` with zero transport calls** (spy the transport, not a flag).
- robots: `/standings/` and `/calendar/` are refused with `ROBOTS_DISALLOWED` and no request; the exemption
  applies only to `allowed_paths_json` **and** only with a credential present.
- **series (the §19 acceptance criterion):** `listing-recurring` produces one `event_series` per family with the
  right `recurrence`, every round `is_recurring_round = true`, **absent from the main-feed reader and present in
  the Contest Calendar reader**; `listing-oneoff` produces `is_recurring_round = false` and **appears in the
  feed**; `listing-yearly` is YEARLY and not a round.
- normalization goldens; no e-mail/phone pattern and no people-shaped key in any produced candidate (D-29).
- the key never appears in a captured log stream, in a snapshot file, or in an export payload.
