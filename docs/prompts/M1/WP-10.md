BUILD:
1. contracts — `dedup.ts`: `DedupFeatures {title, organizer, dateProximity, locationMode, urlMatch}`,
   `DedupScore {total, features}`, `DedupDecision` AUTO_MERGE|CANDIDATE|NEW, `DedupCandidateDto`,
   `MergeRequest`/`UnmergeRequest`, `ConflictDto {field, values: [{value, sourceKey, sourceRecordId, trustRank,
   observedAt}], selected}` and `EventChangeDto`. `EVENT_` ErrorCodes (R12): `EVENT_ALREADY_MERGED`,
   `EVENT_NOT_MERGED`, `EVENT_MERGE_SELF`, `EVENT_CANDIDATE_DECIDED` (`EVENT_NOT_FOUND` exists from WP-08a).
2. Settings per R65, registered by this module — no threshold or weight constant duplicated anywhere in code.
3. `src/domain/dedup/` — **pure**, clock injected (R52), no drizzle/fastify/fs:
   - `normalizeTitle()` strips years, edition words and generic filler ("hackathon", "season", "edition",
     "the") and lower-cases; `titleSimilarity()` is a token-set ratio over that.
   - `organizerSimilarity()`; `dateProximity()` (starts within ±3 days, registration deadlines within ±2 days,
     decaying to 0 at the edge); `locationModeAgreement()` (mode first, then city/country).
   - `candidates(candidate, index)` per §7.5: an identical normalized official or registration URL is a
     near-certain match; otherwise same `edition_year` **and** (starts within ±3 days **or** deadlines within
     ±2 days) **and** trigram overlap on the normalized title.
   - `score()` = the weighted sum, with a **URL match scoring 1.0**; `decide()` = ≥ auto-merge threshold →
     AUTO_MERGE · between the two → CANDIDATE (events stay separate, a PENDING `dedup_candidates` row) ·
     below → NEW. **The R64 edition guard is evaluated first and wins over everything, including the URL rule.**
4. `src/domain/events/resolve.ts` — **pure** field resolution over one event's claims: active override >
   highest `trust_rank` > most recent observation, per field. Material disagreement — **dates more than 1 h
   apart, team size, fee, mode** — sets `has_conflicts` and returns every value with its source. A resolved
   value is always exactly one claim's value or an override: never an average, a midpoint, a spliced string or
   a converted currency.
5. `src/modules/events/link.ts` — the DB side, called from WP-09a's per-item transaction after normalization
   and the WP-08b policies: candidate generation over an indexed slice (`normalized_title`, `edition_year`,
   `starts_at`) → decision → in **one transaction** write the `events` row (insert or update), one
   `event_field_claims` row per field per source record (including WP-09b's R63 alternate claims with
   `is_selected = false`), `source_records.event_id`/`match_method`/`match_score`, a PENDING `dedup_candidates`
   row for the grey band, an `event_changes` row for every **selected** value that changed (cause SCRAPE, with
   the source record), `events.last_changed_at`, `has_conflicts` and `quality_score`. Audited via `withAudit`
   in the same transaction (R35): SYSTEM for auto-merges, USER for admin actions. A `POLICY_HIDDEN` event still
   links and still keeps claims — visibility is not a reason to skip provenance.
6. Merge and unmerge per R66, plus: resolution is recomputed for the survivor, the `dedup_candidates` row moves
   to MERGED or REJECTED with `decided_by`/`decided_at`, and the handoff states what happens to overrides,
   watchlist rows and `event_user_state` on both sides.
7. Review API, **admin only** (§10.2) via `assertCan`, every write audited, `version` optimistic concurrency →
   409: `GET /api/v1/admin/dedup/candidates?status=PENDING` (paged; both events, the score and its feature
   breakdown) · `POST /api/v1/admin/dedup/candidates/:id/merge` · `.../reject` ·
   `POST /api/v1/admin/events/:id/unmerge` · `GET /api/v1/events/:id/conflicts` (the "Sources disagree"
   payload WP-16b renders) · `GET /api/v1/events/:id/changes` (cursor-paged history). No UI. **No new job**:
   linking runs inline with ingest and R22 lists no dedup job.

TESTS (fixture-backed under `apps/backend/test/fixtures/dedup/`, the four §19 scenarios named after themselves
so WP-16b can reuse them):
- **`same event on three sources`** — one hackathon as a college-site record, a Devfolio record and a CTFtime
  record → **one** event with three source records; title and dates resolve to the highest `trust_rank` source;
  every differing field lists all three claims with their sources.
- **`yearly editions never merge`** — "HackX 2025" and "HackX 2026", same organizer, **same official URL** →
  two events, no auto-merge and **no `dedup_candidates` row** (R64).
- **`internal round vs national round`** — same title and year, different dates and mode ("Internal Hackathon"
  vs "National Finals") → separate events plus a PENDING candidate, never auto-merged; merge joins them and
  reject leaves them apart with the row REJECTED.
- **`ctftime prize conflict`** — WP-09b's structured "$500" against "₹50,000" in the description →
  `has_conflicts` true, both claims returned by `/events/:id/conflicts` with their source, the structured value
  selected, **no currency conversion and no arithmetic anywhere in the resolved row**.
- Scoring: raising `dedup.autoMergeThreshold` to 0.95 flips a fixture from AUTO_MERGE to CANDIDATE with no code
  change (R65); a URL match scores 1.0; the feature breakdown is returned with every candidate.
- Resolution: an active override beats a higher-`trust_rank` source and a cleared override falls back; 59
  minutes apart is not a conflict and 61 minutes is; and a property test over conflicting claims asserting
  **every resolved value is byte-equal to some claim or to an override** — nothing averaged or invented.
- Change detection: a re-scrape that moves a registration deadline writes exactly one `event_changes` row (old,
  new, cause SCRAPE, source record); a re-scrape that changes nothing writes none; merge and unmerge write
  their own. **No notification is created** — WP-23 consumes this feed later.
- Reversibility (R66): merge → unmerge restores the pre-merge resolution and both events, with row counts per
  table identical before and after.
- API: a professor gets 403 on every write; a stale `version` gets 409; merging an already-merged event gets
  `EVENT_ALREADY_MERGED` and unmerging a never-merged one `EVENT_NOT_MERGED`; one audit row per action, in the
  same transaction as the change.
