WP-34 — Student edition: a STUDENT role, a guest that needs no sign-up, "Myself" or "An institution" at first run, and release v0.10.0

Owner-directed (10 Oct 2026), milestone **M4.6 — Students**. Junction so far assumes one professor on one machine
(Q1). This WP lets a **student** install the same Junction on their **own** PC and use all of it without creating an
account. On the first run they choose whether they represent **themselves** or **an institution** (a club, a
chapter, a college team), and the app sets itself up for that choice. Students manage their own teams and
competitions. There is no link to any professor's install: student installs are standalone, like department
installs.

| Ruling | Text |
|---|---|
| R130 Installation mode | One setting, `installation.mode` = `DEPARTMENT` · `STUDENT_INDIVIDUAL` · `STUDENT_INSTITUTION`, written by `/setup/complete` inside R40's transaction and never changed by any route afterwards. Its **default is `DEPARTMENT`**, so a v0.9.0 database upgrades with no data change. `GET /setup/status` and `GET /me` both carry it. Changing mode means a fresh data folder (out of scope). |
| R131 The STUDENT role | `ROLE_KEYS` gains `STUDENT`. Its §10.2 row is today **identical to PROFESSOR's**: own teams, competitions, workflows, outcomes and saved items, with every admin action `NEVER`. It is a separate key so the two can diverge, and because a role is the install's vocabulary. The server refuses mixing: `PROFESSOR` can never be granted on a student install, `STUDENT` never on a department install (422 `ROLE_NOT_FOR_MODE`). Every place that means "can mentor" (team/competition mentor pickers, `TEAM_MENTOR_NOT_PROFESSOR`, R105 transfer targets, `TeamFormPage.selfAllowed`) reads a new `MENTOR_ROLE_KEYS = ['PROFESSOR','STUDENT']` instead of the literal `'PROFESSOR'`. |
| R132 The guest | A student install creates one built-in user: `is_guest = 1`, display name "Guest", email `guest@junction.invalid` (reserved, never a login), and a password hash that is **not** a PHC string, which `verifyPassword` rejects without throwing. `POST /auth/guest` (no body, public only on student installs while guest is enabled, 404 otherwise) mints a normal session for it. Guest sessions never auto-lock (there is nothing to unlock with): `autoLockMinutes` is reported as `null` and idle expiry is not enforced for them. The 12 h absolute expiry stays, and the UI silently re-enters as guest when it is reached. Password login, unlock and change-password on the guest answer 403 `GUEST_HAS_NO_PASSWORD`. Audit rows name the actor "Guest". |
| R133 Myself (`STUDENT_INDIVIDUAL`) | The guest holds `STUDENT` + `ADMINISTRATOR` (the machine is theirs: sources, settings, backups). **Create my profile** converts the guest **in place**: same user id, so every team, competition, saved event, search, interest, notification and appearance setting stays theirs. It sets name, e-mail and password, clears `is_guest`, and from then on the app opens to the sign-in screen and `/auth/guest` answers 404. A second profile is refused (409 `SINGLE_PROFILE_INSTALL`). The admin rail collapses to one **Settings** page (location, sources, appearance, backups when they exist); Users, Duplicates, Categories and Audit are hidden, though the server still allows them since the person is an admin. |
| R134 An institution (`STUDENT_INSTITUTION`) | Until the first profile exists the guest holds `STUDENT` + `ADMINISTRATOR` (so setup's R39 gate is satisfied). The **first profile** created becomes the **lead** (`STUDENT` + `ADMINISTRATOR`) and, in the same transaction, the guest drops to `STUDENT` only. The lead adds and removes other profiles under Admin → Users (`STUDENT` only; offering `ADMINISTRATOR` to another member is allowed, and the last-admin guard stays). The guest stays available as a walk-in account, and the lead can turn it off (`auth.guestEnabled`, default on). A guest who creates a profile is asked "Take what Guest made with you?": yes moves the guest's open mentor rows (R105's transfer, reused) **and** its personal rows (`event_user_state`, `watchlist_items`, `saved_searches` + matches, `user_interest_tags`) in one transaction; notifications stay behind. |
| R135 Student records on a student install | Teammates are `students` rows as today, and the owner of a team or competition is its `PRIMARY` mentor row. The UI calls that **Owner** / **Co-owner** on student installs and never shows the word "mentor". The roll number becomes **optional on student installs only**: `students.university_id`/`university_id_key` become nullable, the unique index becomes partial (`where university_id_key is not null`), and the service still requires it on `DEPARTMENT`, so R93's import matching is unchanged there. A profile may link to its own student row (`users.student_id`, nullable FK, unique) through **This is me** on the student form, and the Dashboard's "My competitions" uses that link. Privacy acknowledgement (Q8) still applies to rows about other people. |

BUILD:

1. **Contracts.** `permissions.ts`: `STUDENT`, its total row, `MENTOR_ROLE_KEYS`. `setup.ts`: `InstallationMode`;
   `SetupStatus` + `mode` (null before setup); `SetupRequest` becomes a discriminated union on `mode`. The
   `DEPARTMENT` branch is exactly today's object. The `STUDENT_INDIVIDUAL` branch takes `displayName?` and
   `home {label, lat, lon}`. The `STUDENT_INSTITUTION` branch takes `organization`, `group {name, code?}` (the club or
   chapter: it becomes the managing department) and `campus`. Both student branches also take
   `scraperContactEmail`, and neither takes `admin`, `backupDir` or `backupPassphrase`. `auth.ts`: `AuthUser.isGuest`,
   `MeResponse.mode`, `SessionExpiry.autoLockMinutes` nullable, and `POST /auth/guest` and `POST /me/profile`
   (claim/create) DTOs. `students.ts`: `universityId` optional in create/update (the service enforces it per mode),
   plus `isMe`.
2. **Migration 0033** (0032 is v0.9.1's fresh-install repair) (hand-edit per the drizzle-kit trap in PROGRESS: copy **only the old columns** in every
   rebuild, with `foreign_keys` off around rebuilds and back on with `foreign_key_check` after):
   - Rebuild `roles` for the new CHECK and seed the `STUDENT` row.
   - `users` gets `is_guest INTEGER NOT NULL DEFAULT 0` and `student_id TEXT NULL REFERENCES students(id)`, with a
     unique partial index on `student_id`.
   - Rebuild `students` with nullable `university_id`/`university_id_key` and the partial unique index. Every table
     that references `students` must still pass `foreign_key_check`.
   - Prove it on a copy of a v0.9.0 database: the migration test upgrades a seeded M3 database and every row count
     is unchanged.
3. **Setup.** `SetupService.complete` branches on mode. Each branch is one transaction, as R40 requires.
   - **Student branches:** write `installation.mode`, the organization, a managing department and a primary campus.
     For Myself these are named "Personal" / "Personal" / `home.label`; for an institution they come from the
     request. Also create the guest (R132) with its roles (R133/R134), set `scraper.contactEmail`, and seed the
     default workflow templates through the existing `onCompleted` hook. Generate **no** backup key or recovery
     code, and return `SetupResult` without them (make those fields optional and test both shapes).
   - **R39 gate:** it keeps its meaning, because the guest is an ACTIVE administrator until R134 hands that over.
   - **Backups:** the backup job/route on an install with no key answers "Backups are not set up yet", which is
     not a failure and raises no `BACKUP_FAILED` notification.
   - **Place search:** add `GET /setup/places?q=` (open only while setup is required) for the wizard's location
     picker. It is a prefix search over the offline gazetteer's places and the institutions table, at most 8
     results, `{label, kind: CITY|INSTITUTION, lat, lon, precision}`. Typed coordinates remain the fallback.
4. **Auth & users.** Add `POST /auth/guest` (R132), with the session hook treating it like `/auth/login`. Add
   `POST /me/profile`:
   - On Myself it converts the guest (R133).
   - On an institution it creates a profile from a guest session, optionally with the take-over (R134); the first
     one becomes lead.
   - Rate-limit it like login, and audit everything through `withAudit`.
   - `users.service` refuses PROFESSOR/STUDENT per mode (R131), refuses a second profile on Myself, and lets the
     lead toggle `auth.guestEnabled`.
   - `policy.ts` needs no change beyond the matrix. Prove that with the matrix test.
5. **Mentor vocabulary (R131/R135).** Replace every hard-coded `'PROFESSOR'` that means "can mentor" with
   `MENTOR_ROLE_KEYS` (teams repository, teams errors, transfer service, `TeamFormPage`, assign flow). A student
   creating a team or a competition becomes its PRIMARY row exactly as a professor does today.
6. **Wizard (desktop).**
   - After Welcome, a new **"Who is setting up Junction?"** step offers *A professor or department* (today's flow,
     unchanged) and *A student*.
   - Student → **"Who are you representing?"**, with *Myself* and *An institution (club, chapter, college team)*.
   - **Myself** then asks: your name (optional, "Guest" if blank) → where you are (place picker) → contact address
     (one sentence on why event sites need it) → done.
   - **Institution** then asks: institution (the picker prefers INSTITUTION results) → your group → where the
     campus is → contact address → done.
   - **Done** opens straight into the app as Guest. No sign-in screen, no recovery screen.
   - Keep `wizard-state.ts` pure, with the step list derived from the mode, so `validateStep`/`nextStep` stay
     unit-testable.
   - Use `Guide` blocks on the two new choice steps to explain the difference in one paragraph each.
7. **Desktop app on student installs.**
   - **Startup:** while the guest is enabled and (Myself) unclaimed, the app signs in as guest by itself. On an
     institution, the sign-in screen gains **Continue as guest** next to the profile sign-in.
   - **User menu:** **Create my profile** for a guest, **Sign out** for a profile. There is no Lock for a guest.
   - **Rail:** Students reads **Teammates** ("People you compete with"). Insights wording swaps "your department"
     for "you" (Myself) or the group's name (institution). The mentor columns and pickers read Owner/Co-owner.
   - **Admin:** Myself sees the single Settings page; the institution lead sees Users (members) + Settings.
   - **Command palette:** gets the same labels.
   - **About dialog:** shows the mode.
   - **Implementation:** one `useInstallation()` hook supplies mode and labels; no component branches on the raw
     string.
8. **Release v0.10.0.**
   - Bump the version (desktop package.json, tauri.conf.json, `version.ts`) and run
     `pnpm --filter @compintel/desktop release`.
   - Install the built exe silently into a clean `%LOCALAPPDATA%` profile folder and drive it over the CDP port
     (method in PROGRESS) through **all three** first runs: Department (unchanged), Myself and Institution.
   - Also upgrade a v0.9.0 data folder in place and confirm it opens as DEPARTMENT with its data.
   - Update README (a "For students" section, three short paragraphs) and publish GitHub release **v0.10.0** on
     `persxn/junction` with the installer, its `.sha256` and notes naming the student edition.

TESTS (the awkward cases, not the happy path):
- **Matrix:** STUDENT row total; `STUDENT` ≡ `PROFESSOR` today (assert equality, so the day they diverge is a
  conscious edit); PROFESSOR on a student install and STUDENT on a department install → 422.
- **Guest:**
  - Password login, unlock and change-password as guest → 403 `GUEST_HAS_NO_PASSWORD`.
  - `/auth/guest` → 404 on a DEPARTMENT install, after a Myself claim, and with `auth.guestEnabled` off.
  - A guest session past idle time still works; past 12 h it is refused.
  - `verifyPassword` on the sentinel hash returns false and does not throw.
- **Claim:**
  - **Myself:** every owned row keeps its owner id; a second profile → 409; afterwards the app opens to sign-in.
  - **Institution:** the first profile is lead and the guest loses ADMINISTRATOR in the same transaction, so a crash
    mid-way leaves the old state.
  - **Take-over:** the take-over moves personal rows and open mentor rows but not notifications; declining moves
    nothing.
  - **Concurrency:** two guests claiming concurrently → exactly one lead.
- **Setup:**
  - Each mode writes exactly its rows; a student request carrying `admin`/`backupPassphrase` → 400.
  - `/setup/places` → 409 after setup; an empty query returns nothing, not everything.
  - The R39 gate is closed before and open after for all three modes.
- **Students:**
  - A roll number is required on DEPARTMENT and optional on student installs.
  - Two teammates with no roll number can coexist; two with the same roll number cannot.
  - **This is me** is unique per profile.
- **Migration:** a v0.9.0 fixture upgrades with identical row counts, `foreign_key_check` is empty, and the mode
  reads DEPARTMENT.
- **UI:**
  - The wizard step sequence per mode (pure).
  - Guest auto-entry, Continue as guest, and Create my profile (both modes).
  - No "mentor"/"Professor" text anywhere on a student install: render every rail route and grep the DOM.
  - The DEPARTMENT install renders exactly as before; existing snapshots/tests unchanged.
  - axe on both new wizard steps, the guest sign-in screen and Create my profile, at CALM and SHOWCASE.
