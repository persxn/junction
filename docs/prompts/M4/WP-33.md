WP-33 — Appearance system: Catppuccin palettes, effect tiers (Calm / Standard / Showcase), motion & glow layer, and the Insights surface

Runs after WP-27b, immediately before M5 (§19, milestone **M4.5 — Delight**). It is the last WP before
hardening, which is deliberate: by now every screen, every data model and every number the app can show
exists, so this WP makes the app *feel* like something worth opening every morning without inventing a
single new fact.

BUILD:

1. **Palette layer under the existing tokens (R67).** WP-06's `--ci-*` semantic tokens are a contract —
   **do not rename one.** Add a *palette* layer beneath them: `src/styles/palettes/{classic,latte,
   frappe,macchiato,mocha}.css`, each defining raw ramp variables, and the `--ci-*` semantic tokens
   mapping onto whichever palette is active. Catppuccin **Latte** becomes the default light flavour and
   **Mocha** the default dark; **Classic** (WP-06's neutrals) stays selectable and is what CALM +
   Classic gives you, i.e. today's app, unchanged.
   - The contrast test from WP-06 is the arbiter, not the palette author: every text-on-surface pair in
     **every flavour** must measure ≥ 4.5:1 (≥ 3:1 for large text and UI boundaries). Catppuccin's
     accent hues will not all pass on their own base — so accents are used for **non-text** roles
     (borders, glows, chart marks, fills) and text uses the `text`/`subtext` ramp. Adjust the mapping
     until the test passes; never exempt a pair.
   - Theme selection is per user and survives re-login: one `settings` key per user via the registry
     (`appearance.flavourLight`, `appearance.flavourDark`, `appearance.effects`, `appearance.rgbPreset`).
     The existing light/dark/**system** mode from WP-06 keeps working and chooses *which* flavour applies.
2. **Effect tiers (R68)** — one setting, three values, honest degradation:
   - **CALM** — no decorative motion or glow at all. Functional transitions only (§16.3's 120–200 ms
     ease-out for drawers, popovers, list changes). Forced whenever `prefers-reduced-motion: reduce` is
     set, regardless of the stored setting.
   - **STANDARD** (default) — subtle: gradient surfaces, hover and focus glows, shimmer skeletons,
     eased progress bars, animated numeric counters, staggered list entrance capped at ~200 ms total.
   - **SHOWCASE** — the full treatment: animated gradient borders, glow pulses on urgency states, the
     RGB presets below, gradient text sweeps on headings and celebratory one-shots on real milestones.
   - Implement as a single `data-effects` attribute on `<html>` plus one CSS layer
     (`src/styles/effects.css`). **No effect may carry meaning by itself** — §16.3's "never colour
     alone" extends to "never glow alone": every state keeps its icon + label, and CALM must lose zero
     information.
3. **RGB presets (R68).** Named presets — *Aurora*, *Synthwave*, *Mocha Glow*, *Off* — driving a hue
   cycle on accent borders and glows, with a speed control (slow / medium / fast / static). Rules:
   applies to borders, glows and accent fills only, **never to text or to a status colour**; the cycle
   pauses when the window is hidden or minimized to tray (see the budget below); off by default at
   CALM and STANDARD, selectable at SHOWCASE.
4. **Motion vocabulary.** Prefer CSS animations and the Web Animations API; if you reach for a library,
   justify it in the report, pin the exact version, run `pnpm audit:deps`, and state the bundle-size
   delta — a decorative dependency that costs more than 15 kB gzipped is not worth it here.
   Ship: shimmer skeletons (replacing WP-06's static `Skeleton` at STANDARD+), determinate progress bars
   with eased fills for workflow/stage progress, animated counters for the Dashboard KPI strip
   (instant at CALM), staggered Discover list entrance, and a gradient sweep on the Assistant's streamed
   answer. Every one of them must be correct at CALM with the animation removed.
5. **Performance budget — this is the part that can break M5, so it is an acceptance criterion, not a
   note.** Animate only compositor-friendly properties (`transform`, `opacity`, `filter`); nothing that
   triggers layout. All decorative animation **stops when the document is hidden**
   (`visibilitychange`) and when the window is in the tray — WP-32 runs a **72-hour tray soak**, and an
   app quietly cycling a gradient for three days on a professor's machine is a bug, not a feature.
   Target: 60 fps on the 8 GB reference tier at SHOWCASE, and **≈ 0 % CPU when idle in the tray at
   SHOWCASE**. Measure both; put the numbers in the report.
6. **Insights surface (R69)** — new route `/insights`, in the left rail (§16.1), and the substantive half
   of this WP. Every number is a deterministic SQL read model over rows that already exist; nothing is
   estimated, extrapolated, or produced by the LLM.
   - Participation over time (events assigned / competitions active per month) · events by type and mode ·
     the engagement funnel with conversion between CONSIDERING → ASSIGNED → APPLIED → PARTICIPATING →
     COMPLETED · outcome distribution (WINNER / RUNNER_UP / FINALIST / QUALIFIED / PARTICIPATED) ·
     per-student and per-team participation counts · mentor load · deadline-hit rate (met vs missed from
     `event_deadlines` + stage completion) · **source contribution** (which ingestion source produced the
     events that actually got assigned — the loop back to M1 that tells the owner which scrapers earn
     their keep) · streaks ("weeks with at least one active competition").
   - Backend: read models in the events/engagements modules with their own tests; one
     `GET /api/v1/insights?from=&to=` returning a typed DTO; respects the permission matrix (a professor
     sees the department-wide open view per D-03, not a private one).
   - Charts: hand-rolled SVG is the default answer for six to eight chart shapes; a library needs the
     same justification as step 4. Every chart has a text or table fallback and an `aria` summary, never
     encodes meaning in colour alone, and renders correctly in all five flavours.
   - Empty state for a fresh install that says what will appear here once competitions exist, not a page
     of zeros.
7. **Rewarding, not manipulative (R69).** Milestones are allowed — first recorded WINNER outcome, a 10th
   completed competition, a four-week streak — as a one-shot, dismissible celebration at STANDARD+,
   never blocking, never repeated, never fabricated, and never a nag to come back. No streak-loss
   warnings, no artificial urgency, no counters that exist only to be incremented. If the underlying
   fact is not in the database, it does not appear on screen.

TESTS (in `pnpm verify` unless stated):
- contrast: the WP-06 measured-contrast test extended to a **matrix of all five flavours × both modes**;
  every text/surface pair ≥ 4.5:1, every UI boundary ≥ 3:1. This test is the gate on the palette work.
- CALM is total: read `effects.css` with `node:fs` (vitest does not process CSS — PROGRESS.md) and assert
  the CALM scope declares no `animation` and no decorative `transition`; and a component test asserting
  a forced `prefers-reduced-motion: reduce` yields CALM behaviour **even when the stored setting says
  SHOWCASE**.
- information parity: for a sample of status/urgency components, render at CALM and at SHOWCASE and
  assert identical accessible names and text content — the glow adds nothing a screen reader loses.
- visibility: simulate `visibilitychange` → hidden and assert decorative animations are stopped/paused.
- settings: the four `appearance.*` keys round-trip through the registry and survive sign-out/sign-in;
  an unknown flavour or preset falls back to the default instead of rendering unstyled.
- insights read models: seeded fixture data with hand-computed expected aggregates for every panel,
  including the awkward ones — a month with zero activity, a student in two competitions for different
  events, a withdrawn engagement (excluded from the funnel's completion rate but visible in totals), and
  a deadline with no due date.
- insights API: permission matrix (professor vs admin), date-range bounds per A7, empty database → empty
  state, not an error.
- axe clean on `/insights` and on one representative existing route at each of CALM / STANDARD /
  SHOWCASE.
- **Outside verify:** the frame-rate and idle-CPU measurements from step 5, run manually on the built exe
  and pasted into the report with the method used.

ACCEPTANCE: `pnpm verify` green · the contrast matrix passes for all five flavours · CALM loses no
information and is forced by reduced-motion · idle tray CPU at SHOWCASE ≈ 0 % and 60 fps measured (state
the numbers and how) · Insights numbers reconcile with the list views they summarise (check at least the
active-competition count against the Competitions screen and say so) · no `--ci-*` token renamed ·
`pnpm audit:deps` clean · any added dependency justified with its bundle cost · files < 400 lines.

OUT OF SCOPE: new data collection of any kind (no telemetry, no usage analytics — the Insights screen
reads what the app already stores) · AI-generated commentary on the charts (§9 is read-only and WP-27b
owns the Assistant) · changing the semantic token contract · the tray's own visuals (R29 gives those to
WP-30) · export of insights (WP-28 owns exports; wire the button to it only if WP-28 already shipped) ·
gamification that rewards anything other than recorded outcomes.
