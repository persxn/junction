b) Append to the §21 table:
| R106 One deadline read model | `v_deadlines` is a SQL **view** (custom migration), not a table and not a per-screen query: it stores nothing, so it can never disagree with its sources, and the Radar, the KPI strip and the evaluator all read one definition. Rows: event deadlines of VISIBLE, non-cancelled events that someone has saved or that have an active competition (ASSIGNED · APPLIED · PARTICIPATING); due dates of non-COMPLETED, non-SKIPPED stages and of open tasks in active competitions. The view has no user column: scope (mine · team · all) is a join in the repository. A past **event** deadline leaves the model — only our own work (stage, task) is ever OVERDUE. A DATE-precision `due_at` is the end of that day in the event's zone (ADR-0015); buckets are cut on Asia/Kolkata calendar days (A7). | §12, §6.4, ADR-0015 |
| R107 Radar buckets are disjoint; a KPI is its list's own count | Supersedes §12's cumulative Today/3/7/30 counts: the Radar groups by §6.4's urgency band — OVERDUE · TODAY · ≤ 3 DAYS · ≤ 7 DAYS · LATER — each item in exactly one bucket, with §12's "Event deadlines / Our work" split kept as a filter. Every Dashboard KPI is defined once as the filter of the list it opens (an `EventQuery`, a competitions filter or a Radar filter) and its number is that list's total computed by that list's code path — never a separate COUNT. | §12, §16.2, §19 |

BUILD:
1. **Pure domain** (`src/domain/deadlines/`, lint boundary applies, `Clock`-injected, no SQL):
   `bucketBounds(now, tz)` → the four instants that cut OVERDUE/TODAY/≤3/≤7/LATER (end of today, of today+3,
   of today+7, on Kolkata days via pre-M1's A7 helpers — DST-free zone, still use the helper); `urgencyOf(dueAt,
   bounds)`; and **`dueItems(rows, now)`** → `DueItem[]` {itemKind EVENT_DEADLINE|STAGE|TASK, deadlineKind,
   label, dueAt, precision, bucket, daysLeft, eventId, engagementId?, teamId?, stageId?, taskId?,
   sourceLabel}. This is the hand-over to WP-23: it adds thresholds, recipients and dedupe on top, and never
   re-derives a bucket.
2. **Migration** (`db:generate:custom`, next free number, never `push`; `pnpm typecheck` first): `v_deadlines`
   per R106 — `event_deadlines` ∪ stages ∪ tasks, with `event_id`, `engagement_id`, `team_id`, stage/task ids,
   `origin` and the source name for "Stated by Devfolio". First check whether `events.registration_deadline_at`
   / `submission_deadline_at` always have an `event_deadlines` row; if not, union them guarded by `NOT EXISTS`
   so **no deadline appears twice** (test it). Test that the view exists after migrate and drizzle leaves it alone.
3. **Repository** (`modules/deadlines/repo.ts`, SQL only here): one `whereFor({scope, teamId?, group?, bucket?},
   bounds, userId)` used by both `countsByBucket()` and `list()` (keyset cursor, due_at then id). Scopes (D-03):
   **mine** = events I saved + competitions where I am an active primary/co-mentor · **team** = that team's active
   competitions · **all** = every active competition in the department + events I saved (saving is personal).
4. **API**: `GET /api/v1/deadlines?scope&teamId&group&bucket&cursor` → items + `counts` per bucket, bucket
   computed server-side at request time (the UI never recomputes it, only ticks the countdown);
   `GET /api/v1/dashboard/kpis?scope` → each tile `{key, value, totalIsApproximate, link}` where `link` is the
   serialized list filter the tile opens.
5. **KPIs** (`modules/dashboard/kpis.ts`, one definition each, R107): *Upcoming events* = the Discover query
   `{eventDate:{from: today}, excludeHidden}` → Discover "All events" with those chips · *Closing soon* = WP-16a's
   Closing-soon preset query, counted by the search module's own path · *Active competitions* = WP-19's list
   filter on the active statuses → Competitions list · *Overdue tasks* = Radar `{itemKind TASK, bucket
   OVERDUE, scope}` → `/deadlines`. The tile formats its number with **the same formatter** as the list header
   (so an approximate total reads identically). Dashboard has one scope toggle, Mine · All (default Mine),
   applying to the last two tiles and the Radar panel; event tiles are global.
6. **Deadline Radar** (`features/deadlines/`, route `/deadlines`, "View all" from the Dashboard): groups by bucket
   with a count per group heading; filters scope · team picker · Event deadlines / Our work; each row: urgency
   **icon + words** ("Overdue by 2 days", "Due today", "In 3 days", "Later — 14 Oct"), label, owner
   (competition · team · event, each a link), source ("Stated by Devfolio" · "Entered manually" · "Workflow stage"
   · "Task"), and precision honestly: "27 Sep (time not stated)", "Oct (date not stated)" — **never 00:00**.
   Skeleton, empty ("Nothing due — saved events and competitions show their deadlines here"), error with retry.
7. **Dashboard** (§16.2, replaces the placeholder route): KPI strip · Radar top 8 (non-empty buckets first) ·
   Nearby (WP-16a preset, 5 cards) · Recommended (RELEVANCE, no text, 5 cards, each with its WP-15b reasons
   visible) · Active teams with progress (WP-20a progress + schedule health **with its reason**) · Recent
   notifications — an empty-state card WP-23 replaces. Each panel loads, fails and empties on its own.
8. **Job** (R22): register `deadline-evaluator` — GENERAL class, every 5 min, **not network-gated** (D-23: it
   must run offline). Its body reads `v_deadlines` for all active scopes, calls `dueItems(now)` and hands the
   result to each registered `DueItemSink`; WP-22 registers **none** and logs `{items, byBucket}`. Export
   `registerDueItemSink()` — that is WP-23's seam. Extend `seed:demo` (synthetic, D-33) with competitions,
   stages and tasks whose due dates land in every bucket and every precision.

TESTS (injected clock, no real sleeps):
- Bucket edges on Kolkata days: 23:59:59 IST today vs 00:00 tomorrow; a DATE deadline "today" stays TODAY until
  the Kolkata day ends; an event in another zone with DATE precision; UTC-midnight-crosses-IST-date cases.
- R106: a completed stage, a done task, a SKIPPED stage, a hidden/merged/cancelled event, a past event deadline
  and a CONSIDERING competition are all absent; a past open task **is** OVERDUE; no row appears twice.
- Scope: a co-mentor whose period ended loses "mine"; a saved event with no competition is in mine and all.
- **Counts match list views** (the §19 AC, literally): for every scope × bucket × group, `counts[bucket]` =

  real list endpoint. UI (jsdom): clicking each tile lands on the list with exactly the tile's filter as chips.
  `pnpm e2e`: sign in → Dashboard → click each of the four tiles → the list's total text equals the tile's.
